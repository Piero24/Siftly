# Versioning and Releases

This page defines the official Siftly release flow for alpha, beta, rc, and stable versions.

## Canonical Release Flow

Siftly now uses **Release Please** as the release entrypoint.

1. Merge Conventional Commit PRs into `main`.
2. `release-please.yml` opens or updates a release PR.
3. CI auto-syncs metadata-derived files on the release PR branch.
4. Review and merge the release PR.
5. CI runs a fallback metadata sync on `main` after merge (self-healing).
6. Release Please creates the tag and GitHub Release.
7. Tag-triggered workflows publish extension and Docker artifacts.

Normal flow: no manual version edits in multiple files and no manual tag creation.

Default bump policy is patch-only (`x.y.z -> x.y.(z+1)`) unless you explicitly choose a different version strategy.

## Single Source of Truth for Version

Version starts in `metadata.json` (`version`).

`npm run metadata:sync` propagates that version into:

- `package.json`
- `public/manifest.json`
- `documentation/package.json`
- `README.md` version badge
- `.release-please-manifest.json`

CI and release workflows run `npm run metadata:verify` to prevent drift.

## Supported Version Formats

Use SemVer with prerelease identifiers:

- Alpha: `1.2.0-alpha.1`
- Beta: `1.2.0-beta.1`
- RC: `1.2.0-rc.1`
- Stable production: `1.2.0`

## Tag Format

Tags are generated by Release Please and include component name + version:

- `siftly-v1.2.0-alpha.1`
- `siftly-v1.2.0-beta.1`
- `siftly-v1.2.0-rc.1`
- `siftly-v1.2.0`

## Outcome Matrix

| Version kind      | Example version | Example tag            | GitHub Release  | Chrome Web Store | Docker deploy |
| ----------------- | --------------- | ---------------------- | --------------- | ---------------- | ------------- |
| Alpha/Beta/RC/Dev | `1.2.0-beta.1`  | `siftly-v1.2.0-beta.1` | Prerelease      | Skipped          | Runs          |
| Stable            | `1.2.0`         | `siftly-v1.2.0`        | Regular release | Published        | Runs          |

Prerelease detection for extension publish still checks `package.json` version content (`alpha`, `beta`, `rc`, `dev`), which remains synced from `metadata.json`.

## Contributor Checklist

When changing release-related metadata:

1. Edit `metadata.json`.
2. Run:

```bash
npm run metadata:sync
npm run metadata:verify
```

3. Commit using Conventional Commits.
4. Merge to `main`.
5. Merge the generated release PR when ready.

## Emergency / Manual Release Path

Manual tag-based release is still technically possible (because downstream workflows trigger on tags), but it is not the standard process and should be used only for emergency recovery.

If used, ensure metadata is synced first:

```bash
npm run metadata:verify
```

## Troubleshooting

### CI fails after merging the Release Please PR with metadata drift

Typical error:

`metadata sync check failed. Run "npm run metadata:sync" to update: documentation/package.json, public/manifest.json, README.md`

What it means:

- `metadata.json` was bumped, but one or more derived files were not committed in the release branch.
- The fallback sync on `main` should self-heal this; if branch protection blocks push-back, CI still warns and may require one manual sync commit.

Recovery steps:

1. Run `npm run metadata:sync`.
2. Commit synced files.
3. Push to `main`.
4. Re-run failed workflow.

### Release PR appears as merged by your user instead of the bot

This is normal. The merge actor is the user who clicks merge. What matters is that the release PR checks passed and metadata was synced before/after merge.
